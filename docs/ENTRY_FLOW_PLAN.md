# План точек входа и привлечения

Обновлено: 2026-05-14

## Статус

- `готово` `/signup`: отдельная русская страница регистрации.
- `готово` `/login`: страница входа больше не смешивает вход и регистрацию.
- `готово` `/login?mode=signup`: старые ссылки мягко переводятся на `/signup`.
- `готово` публичные кнопки на лендинге ведут на `/signup`.
- `готово` регистрация принимает `source`, `ref`, `utm_*` и сохраняет источник в
  Supabase user metadata для будущей админки лидов.
- `сохранено` reference-скриншоты регистрации/оплаты/онбординга конкурента:
  `docs/research/onboarding-reference/`.
- `выявлено` production Supabase сейчас self-hosted; Auth работает через
  `supabase_auth_*`, SMTP направлен в локальный Inbucket/Mailpit, email
  autoconfirm включен. Реальная transactional-почта для кодов подтверждения не
  настроена.
- `готово` `/setup` больше не является сломанной точкой входа: маршрут оставлен
  как совместимый alias на `/settings`, а новые редиректы ведут сразу в
  настройки.
- `готово` создание первого кабинета синхронизирует HttpOnly cookie
  `active_tenant_id`, чтобы продуктовые страницы и API сразу видели активный
  магазин.
- `готово` `/onboarding`: отдельный первый запуск после регистрации. Порядок:
  приветствие, выбор пакета, WB-ключ, trial-подписка, запуск sync в фоне,
  стартовый light dashboard.
- `готово` создание первого кабинета автоматически создает trial-подписку по
  выбранному пакету и выводит клиента в существующую админскую модель подписок.
- `готово` минимальная таблица лидов и раздел `/admin/leads`.
- `нужно` добавить email-code подтверждение регистрации и нормальную доставку
  писем до включения обязательной верификации.

## Решение

Основная регистрация должна идти через сайт:

- сайт контролирует аккаунт, пароль, платежи, подключение магазина и юридические
  тексты;
- Телеграм-канал нужен для привлечения, прогрева и кейсов;
- Телеграм-бот нужен для вопросов, сбора заявок, поддержки, уведомлений и
  привязки аккаунта, но не как основной способ регистрации;
- админ-панель остаётся центром контроля клиентов, магазинов, подписок, оплат,
  проблем синхронизации и будущих лидов.

## Текущий путь

1. Пользователь приходит из сайта, канала, бота, рекламы или рекомендации.
2. CTA ведёт на `/signup`.
3. `/signup` создаёт аккаунт и сохраняет источник регистрации.
4. После входа пользователь попадает в `/onboarding`: выбирает пакет,
   подключает магазин Вайлдберриз и запускает первую синхронизацию.
5. Администратор платформы смотрит аккаунты, магазины, подписки и операционное
   состояние в `/admin`.

## Целевой путь регистрации

1. Пользователь открывает `/signup`.
2. Вводит имя, email, телефон и принимает пользовательское соглашение.
3. Создает пароль.
4. Видит короткий экран приветствия: аккаунт создан, дальше нужно подключить
   магазин.
5. Выбирает пакет.
6. Подключает WB API-ключ и название магазина.
7. Система создает пробную подписку по выбранному пакету и запускает первую
   синхронизацию в фоне.
8. Пользователь сразу попадает в стартовый кабинет, где видит прогресс
   синхронизации, подсказки по сервису и первые понятные действия.

Не держать пользователя на экране синхронизации до полного завершения загрузки:
первая загрузка может быть долгой, а ценность продукта лучше показывать сразу.

Email-код не делаем обязательным барьером перед первым запуском. Email можно
помечать как `unverified` и просить подтвердить позже: перед восстановлением
доступа, сменой email, документами, командными приглашениями и billing-действиями.

## Связка с админкой и подписками

Любой шаг onboarding должен иметь операционный след в админке:

- регистрация создает пользователя/лид с источником (`source`, `ref`, `utm_*`);
- подключение WB-ключа создает tenant, участника-owner и активный tenant cookie;
- выбор пакета должен создавать или обновлять запись в `subscriptions`;
- оплата должна создавать `payments` и `billing_events`;
- админка должна показывать: аккаунт, магазины, выбранный пакет, статус оплаты,
  статус подписки, дату окончания, статус WB-ключа и статус первой
  синхронизации.

Запрещенный вариант: сделать красивый onboarding отдельно от backoffice. Если
пользователь выбрал пакет или оплатил, это сразу должно быть видно в
`/admin/customers` и `/admin/subscriptions`.

## Почта и доставляемость

Письма с кодом могут уходить в спам по типовым причинам:

- отправитель без нормальных SPF/DKIM/DMARC;
- новый или непрогретый домен отправителя;
- отправка с дефолтного/технического SMTP без репутации;
- несовпадение домена сайта, From и return-path;
- слишком рекламный шаблон письма;
- кириллический домен в email-контуре может хуже проходить фильтры, чем
  отдельный ASCII-домен.

Решение для production:

- выбрать transactional-провайдера: Postmark, Resend, Mailgun, AWS SES или
  Яндекс 360/почтовый SMTP, если нужен российский контур;
- использовать ASCII-домен отправителя, например `mail.pro-cifry.ru`, даже если
  основной сайт остается на кириллическом домене;
- настроить SPF, DKIM и DMARC;
- в Supabase Auth выключить autoconfirm и подключить реальный SMTP через
  `GOTRUE_SMTP_*`;
- сделать короткий шаблон письма с 6-значным кодом, названием сервиса и
  понятным текстом "если это были не вы, игнорируйте письмо";
- добавить resend-таймер, rate-limit и лог событий отправки/подтверждения.

## Пароль

Не копировать жесткий чек-лист "10 символов + заглавная + строчная + цифра +
спецсимвол" как обязательный барьер.

Рекомендация для MVP:

- минимум 8 символов;
- кнопка показать/скрыть пароль;
- подсказка силы пароля, но без блокировки по спецсимволам и регистру;
- запрет очевидно слабых паролей позже через отдельную проверку;
- Supabase/GoTrue `GOTRUE_PASSWORD_MIN_LENGTH` держать синхронно с UI.

Так меньше трения при регистрации, особенно для пользователей с менеджером
паролей. Безопасность лучше добирать email-подтверждением, rate-limit,
session-логами и будущей MFA для админов.

## Supabase Auth: решение

Текущий рекомендуемый вариант — оставить Supabase Auth, но довести production
контур:

- у нас уже завязаны Supabase session cookies, `getUser()`, middleware,
  dashboard guard и tenant bootstrap;
- самописный auth добавит риск: хранение паролей, reset, OTP, rate-limit,
  сессии, audit, CSRF, админские блокировки и миграции;
- для текущего этапа дешевле и надежнее настроить Supabase Auth правильно, чем
  переписывать вход.

Варианты:

- `A. Оставить self-hosted Supabase` — минимум изменений, нет MAU-биллинга
  Supabase Cloud; ответственность за SMTP, обновления, backup и мониторинг на
  нас. Это лучший текущий вариант.
- `B. Перейти на Supabase Cloud` — меньше ops, управляемая auth/db-платформа,
  но появится vendor billing и миграция.
- `C. Собственный auth` — не делать сейчас. Имеет смысл только при очень
  специфичных требованиях, которых пока нет.
- `D. Clerk/Auth0` — можно рассмотреть позже, если понадобится polished auth
  без собственного обслуживания, но это отдельная интеграция и стоимость.

По Supabase Cloud на 2026-05-13: pricing указывает Free/Pro лимиты по Monthly
Active Users, а не по общему числу созданных аккаунтов. MAU — активные
пользователи за расчетный период. Для нашего self-hosted контура лимит
практически задается сервером, Postgres и GoTrue, а не тарифом Supabase Cloud.

## Первый запуск после регистрации

Не показывать внешние новости WB в onboarding. Вместо этого:

- "Что уже подключено": email, WB-ключ, тариф/доступ, синхронизация.
- "Что происходит сейчас": какая часть данных грузится и когда появятся первые
  цифры.
- "Что можно сделать уже сейчас": открыть обзор, заполнить себестоимость,
  посмотреть настройки уведомлений.
- "Что даст сервис": прибыль по товарам, рекламные утечки, остатки, сигналы,
  работа команды.

Первый экран кабинета для нового клиента должен быть отдельным light dashboard,
а не полная рабочая таблица со всеми метриками. Полный dashboard открывать
после появления первых данных или по явной кнопке.

## Ближайшие implementation slices

1. Настроить production SMTP и DNS отправителя.
2. Сделать мягкое email-подтверждение без блокировки первого запуска.
3. Доработать стартовый light dashboard: live-прогресс по источникам sync и
   первые полезные действия.
4. Добавить ручные статусы/комментарии лидов в `/admin/leads`.
5. После утверждения тарифов заменить временные пакетные названия и цены на
   финальную сетку.

## Будущая модель лидов

Следующий безопасный шаг — добавить таблицу лидов и раздел админки:

- email;
- Телеграм id / username, если пришёл из бота;
- источник: сайт, канал, бот, реклама, рекомендация, вручную;
- статус: новый, связались, зарегистрирован, подключил магазин, пробный период,
  оплатил, потерян;
- привязка к `users.id` и `tenant_id`, когда лид стал клиентом;
- utm-метки и комментарий администратора.

Миграцию лидов делать отдельным focused slice, потому что сейчас `schema.ts` и
drizzle-журнал уже изменены параллельной работой по АУСН.

## Что учли

- Next.js SaaS starter показывает стандартную связку: лендинг, тарифы,
  email/password auth, dashboard, billing и роли.
- Dub добавил email/password регистрацию, потому что не всем подходит вход
  через внешние OAuth-провайдеры.
- NIST SP 800-63B поддерживает практику пароля от 8 символов без навязанных
  сложных правил; показ пароля улучшает ввод и работу с менеджерами паролей.
- Telegram Login Widget подходит для будущей привязки аккаунта.
- Telegram deep links подходят для источников вида
  `/signup?source=telegram_bot&ref=start`.
